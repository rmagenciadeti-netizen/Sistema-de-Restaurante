# RM Restaurant SaaS

Ecossistema RM Restaurant SaaS com API modular central, PostgreSQL/Prisma e dois frontends Next.js independentes: RM Restaurant para as operações dos clientes e RM Painel Admin para gestão Master. Integrações fiscais, WhatsApp, pagamentos e impressão física requerem provedor, contrato/homologação e configuração próprios; a API não finge envio ou autorização de terceiros.

## Desenvolvimento local

1. Copie `.env.example` para `.env`; configure segredo JWT aleatório com 32+ caracteres, uma chave `MFA_ENCRYPTION_KEY` de 32 bytes (gere com `openssl rand -base64 32`), origens CORS exatas e credenciais fortes. Preserve uma cópia segura da chave MFA: perdê-la impede descriptografar os segredos dos autenticadores. A API, o worker e o seed carregam o `.env` da raiz como alternativa às variáveis do ambiente e ao `.env` do diretório atual. Para os comandos do banco, exporte as variáveis em cada terminal: `set -a; . ./.env; set +a` (use apenas um `.env` confiável).
2. Inicie o PostgreSQL local: `docker compose up -d postgres`. No Compose de desenvolvimento, ele fica acessível apenas em `127.0.0.1:5432` e usa `postgres/postgres`; não reutilize essa credencial nem exponha essa configuração em produção.
3. Instale pacotes: `npm ci`.
4. Aplique a migração versionada em um banco local vazio: `npm run db:deploy`.
5. Crie o Master: `npm run seed:master`. Configure `MASTER_ADMIN_EMAIL`, `MASTER_ADMIN_USERNAME` e uma senha forte exclusiva no `.env`. O usuário inicial é criado como `Admin`, exige troca de senha no primeiro login e o seed não altera contas existentes. Não há senha padrão `123`. Somente em desenvolvimento (bloqueado com `NODE_ENV=production`), `npm run seed:dev-operator` cria/atualiza um tenant e um usuário ADMIN sem MFA para `POST /api/v1/auth/login` (`DEV_OPERATOR_EMAIL`/`DEV_OPERATOR_PASSWORD` opcionais; padrão `operador@example.com`).
6. Inicie `npm run dev:api`, `npm run dev` e `npm run dev:admin` em terminais separados. O RM Restaurant abre em `http://localhost:3000`; o RM Painel Admin, em `http://localhost:3001`. Os dois frontends compartilham telas e componentes por importação, mas são builds separados, usam chaves de sessão diferentes e o admin exige `MASTER_ADMIN` na rota `/auth/master-login`; todas as rotas administrativas também validam esse perfil no backend. Use os fluxos de licença e senha forte configurados no seed. Ambos usam `/api-proxy` e encaminham para a API em `http://127.0.0.1:4000/api/v1`; quando estiverem em hosts ou contêineres diferentes, ajuste `API_INTERNAL_URL` para uma URL interna acessível por cada servidor Next.

## Identidade visual

O design system web define tokens dourados em `tailwind.config.ts` e cores estruturais preto/branco no tema slate. O chrome é escuro (barra superior com abas Pedidos/Comandas/PDV, status Aberto/Fechado e menu lateral agrupado e pesquisável, em `components/app-shell.tsx`), a área de trabalho é clara com cartões e tabelas de cabeçalho escuro (`components/ui.tsx`). O menu vem de uma única fonte (`apps/web/lib/menu-catalog.ts`), pode ser recolhido no desktop e itens podem ser ocultados por empresa em Configurações › Personalização do sistema (apenas visual; não altera permissões). A logo oficial ainda não está no repositório; até que o arquivo vetorial ou raster seja fornecido, a interface usa somente o nome tipográfico RM Restaurant, sem redesenhar a marca.

Na raiz do repositório, com Node.js 22:

```sh
npm ci
npm audit --audit-level=moderate
DATABASE_URL=postgresql://postgres@localhost:5432/validation?schema=public npm run db:validate
DATABASE_URL=postgresql://postgres@localhost:5432/validation?schema=public npm run db:generate
npm run build --workspace apps/api
npm run test --workspace apps/api   # testes com banco real: RUN_DB_TESTS=1 e DATABASE_URL de um banco migrado e descartável
npm run test --workspace apps/print-agent
npm exec --workspace apps/web -- node --import tsx --test app/orders/page.test.mjs
npm run lint --workspace apps/web
npm run build --workspace apps/web
```

Validação e geração do cliente não conectam ao banco; a URL acima é apenas um exemplo para esses comandos. Para testar `db:deploy` localmente, use o banco de desenvolvimento configurado no `.env`, após revisar a seção de migrações. A CI aplica as migrações em um serviço PostgreSQL 16 limpo e confere o status. O lint web emite avisos para alguns efeitos de carregamento e hidratação existentes; eles não são convertidos em erros de forma a não incentivar mudanças de comportamento fora desta etapa.

## Migrações e dados existentes

Uma migração Prisma inicial foi gerada em modo `--create-only`, inspecionada e aplicada com sucesso a um PostgreSQL 16 descartável e vazio. Ela cria as 20 tabelas do schema atual; nenhum SQL de remoção ou alteração de dados existentes foi gerado. A migração versionada pode ser aplicada a uma base local vazia com `npm run db:deploy`. Antes de implantá-la, revise o SQL e faça backup do banco alvo.

Para um banco que já contém dados ou tabelas, **não aplique cegamente** a migração inicial nem use comandos de reset. Compare o schema e o histórico reais, preserve backups e siga o procedimento oficial de [baseline de banco existente](https://www.prisma.io/docs/orm/prisma-migrate/workflows/baselining), revisando a SQL e executando `migrate resolve --applied` somente quando o schema existente corresponder integralmente à migração. Em implantação, use `npm run db:deploy`; nunca execute `migrate dev` em produção.

## Módulos e endpoints novos

- Painel comercial SaaS (somente Master): `GET|POST /plans`, `PUT /plans/:id`, `POST /plans/:id/duplicate`; o catálogo de módulos fica em `GET /tenants/modules/catalog`. Planos guardam preços mensal, trimestral, semestral e anual, taxas, teste e limites. Editar o catálogo não reescreve módulos ou valores já contratados: cada licença guarda sua própria seleção e snapshot comercial.
- Provisionamento central: `POST /tenants` cria, em uma transação, tenant, unidade matriz, primeiro administrador, licença pendente (quando selecionado um plano), módulos, auditoria e monitor de etapas. Envie `Idempotency-Key` (8–128 caracteres) para obter resposta repetível; reutilizar a chave com conteúdo diferente retorna `409`. A chave e o hash do corpo nunca são devolvidos. `GET /tenants/provisioning` mostra até 200 execuções e `POST /tenants/:id/provision/retry` retoma/verifica sem duplicar unidade, podendo apontar `NEEDS_INTERVENTION` quando falta administrador ativo. Clientes criados antes do monitor não são alterados automaticamente.
- Contrato de licença: `GET|PUT /tenants/:id/license` permite vincular plano, módulo, limite, validade, periodicidade, preço, desconto e taxas negociadas. Os valores ficam como snapshot da licença, não como cobrança ou confirmação de pagamento; gateway e financeiro SaaS ainda precisam de integração explícita.
- CRUD parcial/soft delete: atualizações em `/employees/:id`, `/products/:id` e `/units/:id`; registros operacionais usam status, preservando histórico.
- Produção/KDS: `GET /production/kds?sectorId=...`, `PATCH /production/items/:id/status`.
- Estoque e fichas: interface em `/inventory` e endpoints `GET|POST /inventory/ingredients`, `POST /inventory/ingredients/:id/movements`, `GET /inventory/movements`, `GET|PUT /inventory/recipes/:productId`. Ao avançar um pedido de `OPEN` para `PREPARING`, a API baixa atomicamente o estoque da receita e registra movimentações; sem receita, mantém o fluxo sem baixa. A transição exige saldo suficiente e não pode ser repetida ou revertida pelo fluxo de status.
- Caixa/pagamentos: interface em `/cash` para abertura/fechamento de caixa e registro manual de pagamentos em pedidos com saldo, usando `POST|GET /cash/sessions`, `POST /cash/sessions/:id/close`, `POST|GET /cash/payments`. A interface mostra saldos e diferenças, mas PIX/cartões não são cobrados nem confirmados por provedor externo.
- Entrega: `GET|POST /delivery`, `PATCH /delivery/:id/status`; zonas e taxas em `GET|POST /delivery/zones`, `PATCH /delivery/zones/:id`. Pedidos `DELIVERY` com `deliveryZoneId` somam a taxa e respeitam o pedido mínimo.
- Categorias do cardápio: `GET|POST /products/categories` e `PATCH /products/categories/:id`. A tela de produtos permite atribuir categorias; o cardápio QR agrupa os itens por categoria. O cadastro e edição são restritos à gestão e isolados por empresa.
- Preços em lote: `PATCH /products/prices/bulk` altera até 100 produtos da empresa/unidade em uma transação, exigindo o preço anterior de cada item; uma divergência cancela todo o lote. No catálogo, selecione os itens da página, informe os valores ou calcule uma prévia de aumento/redução percentual sobre os preços atuais, revise e confirme a operação.
- Motor central de pedidos (`apps/api/src/lib/order-engine.ts`): PDV, garçom, QR da mesa e demais canais usam `createOrder`, que valida produtos/mesa/cupom/zona por empresa e unidade, calcula desconto, taxa de serviço (percentual da unidade em pedidos de mesa, dispensável com `applyServiceFee:false`) e taxa de entrega, vincula/cria o cliente e enfileira a impressão dos setores com impressão automática, tudo em transação serializável.
- No PDV, pedidos de mesa exigem unidade; a seleção mostra apenas mesas daquela unidade. A taxa de serviço começa selecionada e pode ser retirada antes da criação do pedido, respeitando o percentual configurado na unidade.
- Os cartões de mesas e reservas com clientes sentados abrem o PDV com a mesa e a unidade selecionadas; pedidos recentes, entregas e histórico do cliente oferecem acesso ao caixa com o pedido selecionado, produtos ativos levam à respectiva ficha técnica e ingredientes podem ser selecionados para reposição em compras. Pedidos de delivery levam ao quadro de entregas com o pedido selecionado quando disponível. Os atalhos respeitam as permissões e o escopo aplicados pela API; as listas de caixa e entregas usam os 100 pedidos mais recentes e avisam quando o pedido não está disponível.
- Produção e impressão: setores (`GET|POST /production/sectors`, `PATCH /production/sectors/:id`) ligados a impressoras (`GET|POST /printing/printers`, `PATCH /printing/printers/:id`, `POST /printing/printers/:id/test`). O produto conhece só o setor; o setor conhece a impressora principal. Cada pedido gera um ticket por setor na fila `PrintJob` (`GET /printing/jobs`, `POST /printing/jobs/:id/retry`, `POST /printing/orders/:orderId/print` para reimpressão). Setor sem impressora ativa gera job `FAILED` reenviável.
- Setores compartilhados podem ter impressoras principais distintas por unidade. A fila prefere a impressora ativa da unidade do pedido e só utiliza impressora compartilhada na ausência de uma local; nunca escolhe a impressora de outra unidade. Setor incompatível ou ausência de impressora gera job `FAILED` para análise.
- Agente de impressão (`apps/print-agent`): serviço Node sem dependências para o computador do restaurante. Crie o agente em `POST /printing/agents` (o token aparece uma única vez; só o hash é guardado) e execute `RM_API_URL=https://.../api/v1 RM_AGENT_TOKEN=rmagt_... npm start --workspace apps/print-agent`. Ele busca jobs em `/print-agent/jobs/next`, imprime em ESC/POS e confirma em `/print-agent/jobs/:id/result` (até 3 tentativas; jobs presos por mais de 2 minutos são reabertos). Impressoras `NETWORK` usam TCP 9100; `USB`, `SHARED` e `SERIAL` recebem bytes brutos no caminho de dispositivo/compartilhamento informado em `address` (Windows: `\\HOST\IMPRESSORA`, `COM3`; Linux: `/dev/usb/lp0`). No Windows, `apps/print-agent/install-windows.ps1` registra uma tarefa agendada que inicia com o sistema e reinicia em falha (não foi executado em Windows neste ambiente).
- Atualização do agente: aplique as migrações e atualize a API e todos os agentes juntos; confirmações agora exigem `claimId` e `attempt` devolvidos pela fila. Retomadas após três tentativas expiradas ficam `FAILED` para análise e reenvio manual. Se a impressora imprimir mas a confirmação se perder, a retomada pode imprimir novamente: verifique o ticket físico antes de reenviar; impressão exatamente uma vez não pode ser garantida pelo protocolo ESC/POS.
- Adicionais e combos: grupos de adicionais (`GET|POST /catalog/modifier-groups`, `PATCH /catalog/modifier-groups/:id`, `POST /catalog/modifier-groups/:id/options`, `PATCH /catalog/modifier-options/:id`) com mínimo/máximo, preço e setor próprio por opção, vinculados a produtos em `PUT /catalog/products/:id/modifier-groups`. Combos em `PUT /catalog/products/:id/combo`: cobrados em uma linha, com cada componente produzido/impresso no seu setor. Pedidos aceitam `items[].modifiers: [{optionId, quantity}]`.
- Mesas e QR: `GET|POST /tables`, `PATCH /tables/:id`, `POST /tables/:id/rotate-qr`. O QR aponta para `/m/<token>` no site; a API pública (`GET /public/tables/:token/menu`, `POST /public/tables/:token/orders`) tem limite próprio, no máximo 10 pedidos abertos por mesa e não permite que pedidos anônimos alterem clientes existentes.
- CRM e LGPD: `GET|POST /customers`, `GET|PATCH /customers/:id`, pontos de fidelidade (1 por real inteiro ao concluir o pedido), `GET /customers/:id/export` e `POST /customers/:id/anonymize` (gerência). Ao ficar `READY`, pedidos com cliente enfileiram a mensagem `order_ready` no outbox.
- Compras e inventário: `GET|POST /purchasing/suppliers`, `GET|POST /purchasing/orders`, `POST /purchasing/orders/:id/receive|cancel`. O recebimento atualiza estoque, custo médio ponderado e gera conta a pagar. `POST /inventory/counts` aplica inventário guiado com ajustes auditáveis.
- Cupons e reservas: `GET|POST|PATCH /coupons` (percentual ou fixo, validade, mínimo, limite de usos aplicado atomicamente) e `GET|POST|PATCH /reservations` (bloqueia a mesma mesa em janela de 90 minutos e respeita capacidade).
- Permissões por perfil (`apps/api/src/lib/permissions.ts`): gerência (`ADMIN`, `MANAGER`) cadastra; financeiro acessa financeiro/relatórios/compras; caixa e garçom vendem; cozinha acessa KDS e fila; entregador acessa entregas.
- WhatsApp: `apps/api/src/lib/whatsapp-cloud.ts` implementa a API oficial (Cloud API) com templates aprovados. Configure `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID` e `WHATSAPP_TEMPLATES` (JSON, ex.: `{"order_ready":{"name":"pedido_pronto","language":"pt_BR","params":["customerName","orderCode"]}}`) e execute `npm run worker --workspace apps/api` (um único processo). Sem configuração a fila permanece `QUEUED`; falhas ficam `FAILED` e podem ser reenviadas em `POST /whatsapp/outbox/:id/retry`. O adaptador foi testado com resposta simulada da API; valide com seu número/templates reais antes de produção.
- Usuários e escalas: `GET|POST|PATCH /users` (apenas administradores concedem `ADMIN`/`MANAGER`; ninguém altera o próprio perfil). Um usuário pode vincular opcionalmente um funcionário ativo no mesmo tenant e escopo; o vínculo é único, auditado e pode ser removido. Funcionário não precisa de login; o vínculo não altera automaticamente permissões nem desativa acesso. `GET|POST|PATCH|DELETE /shifts` (sem sobreposição por funcionário, máximo de 16h).
- Estoque avançado: cancelar pedido devolve ao estoque o consumo registrado e libera o uso do cupom, e exige estornar antes pagamentos confirmados (`POST /cash/payments/:id/refund`, só registro contábil). `POST /inventory/transfers` move estoque entre cadastros de ingredientes com custo médio. Opções de adicional podem consumir ingrediente (`ingredientId` + `ingredientQuantity`).
- Rateio: `PATCH /units/:id` define `serviceFeePercent` e `waiterSharePercent`; `GET /reports/service-fee-distribution` separa a parte do atendente e o fundo restante, e calcula comissão com `commissionPercent` do usuário.
- Auditoria: `GET /audit` oferece histórico somente leitura, paginado e filtrável por ação, tipo de registro, responsável e período. Restrito a administradores e gerentes sem escopo de unidade; os resultados nunca incluem dados de outras empresas.
- Autenticação: login por e-mail ou nome de usuário (case-insensitive), usuários inativos/bloqueados e tenants indisponíveis recebem erro genérico de credenciais. Contas `MASTER_ADMIN` precisam configurar TOTP no primeiro login e apresentar o código a cada novo login; segredos TOTP são protegidos por AES-256-GCM, sessões Master antigas são rejeitadas e códigos de recuperação aleatórios são mostrados uma única vez, armazenados como hashes e consumidos atomicamente. Login, configuração e verificação têm limites de tentativa. O seed Master usa segredo configurado localmente, força troca no primeiro acesso e registra somente o evento da troca, nunca senhas. A sessão JWT expira em 8 horas; senha alterada invalida tokens de sessão e desafios MFA anteriores.
- Recuperação de senha: `POST /auth/forgot-password` envia um link SMTP de uso único, limitado a 30 minutos, e responde de forma genérica para não revelar se o e-mail existe. `POST /auth/reset-password` valida o token, aplica a mesma política de senha forte, registra auditoria e invalida todas as sessões da conta. Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_FROM` e, quando exigido, `SMTP_USER`/`SMTP_PASSWORD`; defina `RM_RESTAURANT_URL` e `RM_ADMIN_URL` para formar os links corretos. Sem provedor e URLs configurados, a API responde indisponível e não finge envio.
- Pagamentos online e fiscal por adaptador: `apps/api/src/lib/providers.ts` define `PaymentProvider` e `FiscalProvider`; registre implementações reais em `apps/api/src/providers.config.ts`. Sem adaptador, `POST /payments/charges` e `POST /fiscal/orders/:id/emit` respondem 501. Webhooks em `POST /payments/webhook/:provider` recebem o corpo bruto e o adaptador deve validar a assinatura. Nenhum adaptador de PIX/cartão/NFC-e acompanha o projeto: contrato, credenciais, certificado e homologação são do provedor escolhido.
- Marketplaces: crie chaves em `POST /integrations` e receba pedidos em `POST /inbound/:provider/orders` (Bearer `rmint_...`, idempotente por `externalId`, itens mapeados por `Product.code`, preços do nosso catálogo, taxa de entrega informada pelo parceiro, cria o job de entrega). Produtos com grupos de adicionais obrigatórios não podem ser mapeados. Devolução de status ao marketplace (ex.: aceitar/despachar no iFood) exige a API do parceiro e não está implementada.
- WhatsApp: `POST|GET /whatsapp/outbox`. O endpoint apenas enfileira um registro auditável; envio real requer adaptador de provedor oficial e worker configurado.
- Financeiro e relatórios: `/financial` permite cadastrar contas a pagar/receber e registrar baixa integral, inclusive de contas geradas por compras. `GET|POST /financial/entries` aceita filtros `type`, `status`, `page` e `pageSize`; `POST /financial/entries/:id/settle` registra a baixa de uma conta aberta com auditoria e escopo de empresa/unidade. A baixa é gerencial, não movimenta dinheiro nem concilia banco. Resumo em `GET /financial/summary`; relatórios em `GET /reports/overview?from=ISO&to=ISO` e `GET /reports/waiters?from=ISO&to=ISO`. O rateio atual limita-se à divisão atendente/fundo descrita acima.

- Licenças e módulos (somente Master): `GET /tenants/modules/catalog`, `GET|PUT /tenants/:id/license` e a tela `/licenses`. Cada empresa pode ter uma licença (`PENDING`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `CANCELLED`), validade, limites de unidades/usuários e módulos contratados. A API aplica a restrição em `requireAuth` (por prefixo de rota) e no login, e os limites na criação de unidades e usuários; ocultar menus não é o controle. Empresas sem licença continuam com acesso integral (ambientes anteriores ao licenciamento) e nenhum dado é apagado por suspensão ou vencimento. Cada alteração gera `LICENSE_UPDATED` na auditoria. Ainda não implementados: chaves offline assinadas, solicitação com código, planos/preços, sincronização com confirmação e financeiro do SaaS. Rotas públicas (QR de mesa) e de máquina (agente de impressão, webhooks) não passam por essa verificação de módulos.

Rotas privadas exigem token Bearer. Os escopos tenant/unidade vêm do usuário autenticado no banco. O login limita tentativas a 10 por 15 minutos; a API aplica um limite geral de 300 requisições por 15 minutos, ambos em memória por processo. CORS aceita origens configuradas, o corpo JSON tem limite e erros internos não são expostos ao cliente. Para múltiplas instâncias, configure um armazenamento compartilhado de limites; atrás de proxy, ajuste e teste `trust proxy` de acordo com sua topologia e aplique limites no gateway antes de expor a API. Há testes de integração com PostgreSQL real cobrindo isolamento entre empresas, permissões, pedidos, impressão, QR, compras e reservas; amplie-os para os demais módulos antes de produção.

- Balança: produtos podem ser vendidos por peso (`soldByWeight`, preço por kg; a linha do pedido guarda `weightKg`, e a ficha técnica passa a significar 1 kg). `GET /scale/lookup?barcode=` decodifica etiquetas de balança (prefixo, código do produto, peso ou preço, dígito verificador EAN-13) conforme `Configurações › Balança`; `GET /scale/export?brand=TOLEDO|FILIZOLA|URANO|URANO_URF32` gera o arquivo de itens (`/scale-file`). Os layouts seguem formatos de itens comumente documentados e precisam ser validados no modelo/firmware real; **o sistema não se comunica com a balança física**, o arquivo é importado pelo operador.
- Agendamento de pedidos: `POST /orders` (e a loja virtual) aceita `scheduledFor`. As regras (habilitado, dias à frente, faixas por dia da semana, período de bloqueio, antecedência HH:mm, fuso) ficam em `Configurações › Agendamento` e valem para todos os canais via `createOrder`. O pedido fica retido (`releasedAt` nulo; não aparece no KDS nem imprime na produção) até `releaseAt` = horário − max(antecedência, maior tempo de preparo); o worker (`npm run worker --workspace apps/api`) libera os vencidos, e `GET /orders` e `GET /production/kds` também liberam sob demanda. `POST /orders/:id/release` libera agora e `PATCH /orders/:id/schedule` reagenda. Telas: `/scheduled` e `/schedule-settings`. O worker não exige mais WhatsApp configurado.
- Configurações da empresa (`GET /settings`, `PUT /settings/:section`): dados, horário (aberto/fechado/horários), entrega/retirada, loja, PDV, balança, agendamento, impressão, ticket, financeiro, margem padrão, contador diário de pedidos e status de pedido personalizados. Preferências de loja, impressão, ticket e financeiro são armazenadas, mas só têm efeito nos módulos que as leem.
- Liberações por senha: senha de administrador do caixa (`POST /settings/admin-password`, hash bcrypt) e `POST|GET /releases` (limite de 5 falhas/15 min por usuário, em memória por processo). Cancelamento e desconto por quem não é gerente exigem a liberação.
- Telas de balcão: `/monitor` (kanban Aceito/Pronto/Saiu para entrega), `/comandas`, `/pdv` (busca/código de barras/balança, modificadores, cliente, agendamento, couvert, desconto/acréscimo, pagamento no caixa), `/scheduled` e `/history`. Pedidos têm número sequencial (`Order.number`).
- Catálogo: promoções por produto (`/promotions`, aplicadas no preço do pedido), exibição das categorias por horário (`/category-schedules`, `/category-hours`), ajuste de preços em massa com prévia (`/product-tools/bulk-adjust/*`, `/bulk-adjust`), código de barras, favorito e parâmetros fiscais no produto.
- Cadastros e financeiro: entregadores (`/couriers`, vinculáveis às entregas), transportadoras, formas de pagamento personalizadas (`/payment-methods`, com `GET /payment-methods/options`), categorias de contas, couvert artístico (`/cover-events`, cobrado por pessoa em pedidos de mesa) e regras tributárias (`/tax-rules`, apenas parâmetros para o provedor fiscal; o sistema não calcula nem transmite impostos).
- Relatórios: `GET /reports/x` e `GET /reports/x/:kind?from&to&format=csv` (vendas, taxa de serviço, couvert, DRE simplificado, cancelamentos, curva ABC, vendas agendadas, produtos vendidos, margem, formas de pagamento, contas a pagar/receber, conferência de fechamentos, zonas de entrega, clientes fiéis, promoções, disponibilidade e atendimentos via robô), reunidos em `/reports?r=<tipo>`.
- Loja virtual: `GET /public/store/:slug` e `POST /public/store/:slug/orders` (sem autenticação, com limite de taxa) alimentam `/loja/<slug>`; o link, o QR Code e o botão Aberto/Fechado ficam em `/store`. O pedido da loja não registra pagamento; forma de pagamento e endereço vão para a auditoria (`STORE_ORDER_DETAILS`).
- Integrações: a aba “PIX, POS e fiscal” lista apenas os adaptadores realmente registrados (`GET /integrations/providers`); maquininhas, PIX e fiscal seguem dependendo de adaptador certificado do provedor.

## Limitações relevantes

Estoque: consumo automático por ficha técnica e por adicionais ao iniciar o preparo, compras com custo médio, inventário guiado, transferências e estorno ao cancelar. Caixa e relatórios são gerenciais, não conciliação contábil. Sem adaptadores reais instalados não há emissão fiscal (NFC-e/NF-e), cobrança PIX/cartão nem retorno de status a marketplaces; a regra de rateio de gorjeta é apenas a divisão atendente/fundo configurada por unidade. Não exponha em produção antes de executar a validação Prisma/TypeScript, migrações, testes de integração e revisão de segurança, incluindo permissões por perfil e escopo de unidades.

Antes de qualquer implantação, revise também `npm audit` e atualize dependências vulneráveis com testes de compatibilidade, configure HTTPS e segredos reais, verifique backups e restauração, e teste concorrência de caixa/pagamentos e isolamento entre tenants com um PostgreSQL real. Esta etapa é um endurecimento inicial, não uma certificação de prontidão para produção.

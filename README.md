# RM Restaurant SaaS

Ecossistema RM Restaurant SaaS com API modular central, PostgreSQL/Prisma e dois frontends Next.js independentes: RM Restaurant para as operações dos clientes e RM Painel Admin para gestão Master. Integrações fiscais, WhatsApp, pagamentos e impressão física requerem provedor, contrato/homologação e configuração próprios; a API não finge envio ou autorização de terceiros.

## Desenvolvimento local

1. Copie `.env.example` para `.env`; configure segredo JWT aleatório com 32+ caracteres, uma chave `MFA_ENCRYPTION_KEY` de 32 bytes (gere com `openssl rand -base64 32`), origens CORS exatas e credenciais fortes. Preserve uma cópia segura da chave MFA: perdê-la impede descriptografar os segredos dos autenticadores. A API, o worker e o seed carregam o `.env` da raiz como alternativa às variáveis do ambiente e ao `.env` do diretório atual. Para os comandos do banco, exporte as variáveis em cada terminal: `set -a; . ./.env; set +a` (use apenas um `.env` confiável).
2. Inicie o PostgreSQL local: `docker compose up -d postgres`. No Compose de desenvolvimento, ele fica acessível apenas em `127.0.0.1:5432` e usa `postgres/postgres`; não reutilize essa credencial nem exponha essa configuração em produção.
3. Instale pacotes: `npm ci`.
4. Aplique a migração versionada em um banco local vazio: `npm run db:deploy`.
5. Crie o Master: `npm run seed:master`. Configure `MASTER_ADMIN_EMAIL`, `MASTER_ADMIN_USERNAME` e uma senha forte exclusiva no `.env`. O usuário inicial é criado como `Admin`, exige troca de senha no primeiro login e o seed não altera contas existentes. Não há senha padrão `123`. Somente em desenvolvimento (bloqueado com `NODE_ENV=production`), `npm run seed:dev-operator` cria/atualiza um tenant e um usuário ADMIN sem MFA para `POST /api/v1/auth/login` (`DEV_OPERATOR_EMAIL`/`DEV_OPERATOR_PASSWORD` opcionais; padrão `operador@example.com`).
6. Inicie `npm run dev:api`, `npm run dev` e `npm run dev:admin` em terminais separados. O RM Restaurant abre em `http://localhost:3000`; o RM Painel Admin, em `http://localhost:3001`. Os dois frontends compartilham telas e componentes por importação, mas são builds separados, usam chaves de sessão diferentes e o admin exige `MASTER_ADMIN` na rota `/auth/master-login`; todas as rotas administrativas também validam esse perfil no backend. Use os fluxos de licença e senha forte configurados no seed. Ambos usam `/api-proxy` e encaminham para a API em `http://127.0.0.1:4000/api/v1`; quando estiverem em hosts ou contêineres diferentes, ajuste `API_INTERNAL_URL` para uma URL interna acessível por cada servidor Next.

## Identidade visual

O design system web define tokens dourados em `tailwind.config.ts` e cores estruturais preto/branco no tema slate. O chrome é escuro (barra superior com abas Pedidos/Comandas/PDV, status Aberto/Fechado e menu lateral agrupado e pesquisável, em `components/app-shell.tsx`), a área de trabalho é clara com cartões e tabelas de cabeçalho escuro (`components/ui.tsx`). O menu vem de uma única fonte (`apps/web/lib/menu-catalog.ts`), pode ser recolhido no desktop e itens podem ser ocultados por empresa em Configurações › Personalização do sistema (apenas visual; não altera permissões). A logo oficial ainda não está no repositório; até que o arquivo vetorial ou raster seja fornecido, a interface usa somente o nome tipográfico RM Restaurant, sem redesenhar a marca.

## Verificação da API

Na raiz do repositório, com Node.js 22:

```sh
npm ci
npm audit --audit-level=moderate
DATABASE_URL=postgresql://postgres@localhost:5432/validation?schema=public npm run db:validate
DATABASE_URL=postgresql://postgres@localhost:5432/validation?schema=public npm run db:generate
npm run build --workspace apps/api
npm run test --workspace apps/api   # testes com banco real: RUN_DB_TESTS=1 e DATABASE_URL de um banco migrado e descartável
npm run test --workspace apps/print-agent
npm exec --workspace apps/web -- node --import tsx --test app/orders/page.test.mjs
npm run lint --workspace apps/web
npm run build --workspace apps/web
```

Validação e geração do cliente não conectam ao banco; a URL acima é apenas um exemplo para esses comandos. Para testar `db:deploy` localmente, use o banco de desenvolvimento configurado no `.env`, após revisar a seção de migrações. A CI aplica as migrações em um serviço PostgreSQL 16 limpo e confere o status. O lint web emite avisos para alguns efeitos de carregamento e hidratação existentes; eles não são convertidos em erros de forma a não incentivar mudanças de comportamento fora desta etapa.

## Migrações e dados existentes

Uma migração Prisma inicial foi gerada em modo `--create-only`, inspecionada e aplicada com sucesso a um PostgreSQL 16 descartável e vazio. Ela cria as 20 tabelas do schema atual; nenhum SQL de remoção ou alteração de dados existentes foi gerado. A migração versionada pode ser aplicada a uma base local vazia com `npm run db:deploy`. Antes de implantá-la, revise o SQL e faça backup do banco alvo.

Para um banco que já contém dados ou tabelas, **não aplique cegamente** a migração inicial nem use comandos de reset. Compare o schema e o histórico reais, preserve backups e siga o procedimento oficial de [baseline de banco existente](https://www.prisma.io/docs/orm/prisma-migrate/workflows/baselining), revisando a SQL e executando `migrate resolve --applied` somente quando o schema existente corresponder integralmente à migração. Em implantação, use `npm run db:deploy`; nunca execute `migrate dev` em produção.

## Módulos e endpoints novos

- Painel comercial SaaS (somente Master): `GET|POST /plans`, `PUT /plans/:id`, `POST /plans/:id/duplicate`; o catálogo de módulos fica em `GET /tenants/modules/catalog`. Planos guardam preços mensal, trimestral, semestral e anual, taxas, teste e limites. Editar o catálogo não reescreve módulos ou valores já contratados: cada licença guarda sua própria seleção e snapshot comercial.
- Provisionamento central: `POST /tenants` cria, em uma transação, tenant, unidade matriz, primeiro administrador, licença pendente (quando selecionado um plano), módulos, auditoria e monitor de etapas. Envie `Idempotency-Key` (8–128 caracteres) para obter resposta repetível; reutilizar a chave com conteúdo diferente retorna `409`. A chave e o hash do corpo nunca são devolvidos. `GET /tenants/provisioning` mostra até 200 execuções e `POST /tenants/:id/provision/retry` retoma/verifica sem duplicar unidade, podendo apontar `NEEDS_INTERVENTION` quando falta administrador ativo. Clientes criados antes do monitor não são alterados automaticamente.
- Contrato de licença: `GET|PUT /tenants/:id/license` permite vincular plano, módulo, limite, validade, periodicidade, preço, desconto e taxas negociadas. Os valores ficam como snapshot da licença, não como cobrança ou confirmação de pagamento; gateway e financeiro SaaS ainda precisam de integração explícita.
- CRUD parcial/soft delete: atualizações em `/employees/:id`, `/products/:id` e `/units/:id`; registros operacionais usam status, preservando histórico.
- Produção/KDS: `GET /production/kds?sectorId=...`, `PATCH /production/items/:id/status`.
- Estados personalizados do KDS: `GET`/`PUT /production/stages` (PUT só gerência; auditoria `KDS_STAGES_UPDATED`). Cada estado (chave, nome, cor) pertence a uma fase real do item (`PENDING`, `PREPARING`, `READY`, `DELIVERED`), em ordem de fluxo, com pelo menos um por fase (4 a 12 estados; padrão Recebido → Em preparação → Pronto → Entregue). `PATCH /production/items/:id/status` aceita `{ status }` **ou** `{ stage }` (nunca os dois) e grava `OrderItem.kdsStage`; as regras de pedido, estoque e histórico continuam usando a fase, e o status geral do pedido não muda. Estado removido ou fora de fase cai no primeiro estado da fase do item. Edição na tela KDS (gerência). Backup agendado do PostgreSQL: ver `docs/BACKUP.md`.
- Pedidos com saldo pendente: `GET /orders?scope=unpaid` (pagamentos CONFIRMED abaixo do total, calculado no banco; usado pelo Caixa). O front revalida GETs JSON com `If-None-Match` (ETag do Express) e reaproveita o corpo no 304.
- Estoque e fichas: interface em `/inventory` e endpoints `GET|POST /inventory/ingredients`, `POST /inventory/ingredients/:id/movements`, `GET /inventory/movements`, `GET|PUT /inventory/recipes/:productId`. Ao avançar um pedido de `OPEN` para `PREPARING`, a API baixa atomicamente o estoque da receita e registra movimentações; sem receita, mantém o fluxo sem baixa. A transição exige saldo suficiente e não pode ser repetida ou revertida pelo fluxo de status.
- Caixa/pagamentos: interface em `/cash` para abertura/fechamento de caixa e registro manual de pagamentos em pedidos com saldo, usando `POST|GET /cash/sessions`, `POST /cash/sessions/:id/close`, `POST|GET /cash/payments`. A interface mostra saldos e diferenças, mas PIX/cartões não são cobrados nem confirmados por provedor externo.
- Entrega: `GET|POST /delivery`, `PATCH /delivery/:id/status`; zonas e taxas em `GET|POST /delivery/zones`, `PATCH /delivery/zones/:id`. Pedidos `DELIVERY` com `deliveryZoneId` somam a taxa e respeitam o pedido mínimo. A saída para entrega é feita no quadro `/monitor`: `POST /delivery/orders/:orderId/dispatch` (pedido pronto + entregador cadastrado ou nome avulso) cria a entrega se necessário, define o entregador e marca como “saiu para entrega”; a tela `/delivery` só acompanha entregas e gerencia zonas.
- Categorias do cardápio: `GET|POST /products/categories` e `PATCH /products/categories/:id`. A tela de produtos permite atribuir categorias; o cardápio QR agrupa os itens por categoria. O cadastro e edição são restritos à gestão e isolados por empresa.
- Preços em lote: `PATCH /products/prices/bulk` altera até 100 produtos da empresa/unidade em uma transação, exigindo o preço anterior de cada item; uma divergência cancela todo o lote. No catálogo, selecione os itens da página, informe os valores ou calcule uma prévia de aumento/redução percentual sobre os preços atuais, revise e confirme a operação.
- Motor central de pedidos (`apps/api/src/lib/order-engine.ts`): PDV, garçom, QR da mesa e demais canais usam `createOrder`, que valida produtos/mesa/cupom/zona por empresa e unidade, calcula desconto, taxa de serviço (percentual da unidade em pedidos de mesa, dispensável com `applyServiceFee:false`) e taxa de entrega, vincula/cria o cliente e enfileira a impressão dos setores com impressão automática, tudo em transação serializável.
- No PDV, pedidos de mesa exigem unidade; a seleção mostra apenas mesas daquela unidade. A taxa de serviço começa selecionada e pode ser retirada antes da criação do pedido, respeitando o percentual configurado na unidade.
- Os cartões de mesas e reservas com clientes sentados abrem o PDV com a mesa e a unidade selecionadas; pedidos recentes, entregas e histórico do cliente oferecem acesso ao caixa com o pedido selecionado, produtos ativos levam à respectiva ficha técnica e ingredientes podem ser selecionados para reposição em compras. Pedidos de delivery levam ao quadro de entregas com o pedido selecionado quando disponível. Os atalhos respeitam as permissões e o escopo aplicados pela API; as listas de caixa e entregas usam os 100 pedidos mais recentes e avisam quando o pedido não está disponível.
- Produção e impressão: setores (`GET|POST /production/sectors`, `PATCH /production/sectors/:id`) ligados a impressoras (`GET|POST /printing/printers`, `PATCH /printing/printers/:id`, `POST /printing/printers/:id/test`). O produto conhece só o setor; o setor conhece a impressora principal. Cada pedido gera um ticket por setor na fila `PrintJob` (`GET /printing/jobs`, `POST /printing/jobs/:id/retry`, `POST /printing/orders/:orderId/print` para reimpressão). Setor sem impressora ativa gera job `FAILED` reenviável.
- Setores compartilhados podem ter impressoras principais distintas por unidade. A fila prefere a impressora ativa da unidade do pedido e só utiliza impressora compartilhada na ausência de uma local; nunca escolhe a impressora de outra unidade. Setor incompatível ou ausência de impressora gera job `FAILED` para análise.
- Agente de impressão (`apps/print-agent`): serviço Node sem dependências para o computador do restaurante. Crie o agente em `POST /printing/agents` (o token aparece uma única vez; só o hash é guardado) e execute `RM_API_URL=https://.../api/v1 RM_AGENT_TOKEN=rmagt_... npm start --workspace apps/print-agent`. Ele busca jobs em `/print-agent/jobs/next`, imprime em ESC/POS e confirma em `/print-agent/jobs/:id/result` (até 3 tentativas; jobs presos por mais de 2 minutos são reabertos). Impressoras `NETWORK` usam TCP 9100; `USB`, `SHARED` e `SERIAL` recebem bytes brutos no caminho de dispositivo/compartilhamento informado em `address` (Windows: `\\HOST\IMPRESSORA`, `COM3`; Linux: `/dev/usb/lp0`). Impressoras `WINDOWS` usam qualquer fila instalada no Windows: o agente lista as impressoras (`Get-Printer`) a cada minuto em `POST /print-agent/printers`, o painel as mostra no campo Conexão › Windows (formulário de impressora e campo “Impressora do setor”) e o trabalho vai como documento RAW (`src/raw-print.ps1`, winspool) só para o agente dono da impressora (`Printer.agentId`); serve para impressoras térmicas ESC/POS com driver instalado, não para formatar em laser/jato de tinta (não foi executado em Windows neste ambiente). No Windows, `apps/print-agent/install-windows.ps1` registra uma tarefa agendada que inicia com o sistema e reinicia em falha (não foi executado em Windows neste ambiente).
- Atualização do agente: aplique as migrações e atualize a API e todos os agentes juntos; confirmações agora exigem `claimId` e `attempt` devolvidos pela fila. Retomadas após três tentativas expiradas ficam `FAILED` para análise e reenvio manual. Se a impressora imprimir mas a confirmação se perder, a retomada pode imprimir novamente: verifique o ticket físico antes de reenviar; impressão exatamente uma vez não pode ser garantida pelo protocolo ESC/POS.
- Adicionais e combos: grupos de adicionais (`GET|POST /catalog/modifier-groups`, `PATCH /catalog/modifier-groups/:id`, `POST /catalog/modifier-groups/:id/options`, `PATCH /catalog/modifier-options/:id`) com mínimo/máximo, preço e setor próprio por opção, vinculados a produtos em `PUT /catalog/products/:id/modifier-groups`. Combos em `PUT /catalog/products/:id/combo`: cobrados em uma linha, com cada componente produzido/impresso no seu setor. Pedidos aceitam `items[].modifiers: [{optionId, quantity}]`.
- Mesas e QR: `GET|POST /tables`, `PATCH /tables/:id`, `POST /tables/:id/rotate-qr`. O QR aponta para `/m/<token>` no site; a API pública (`GET /public/tables/:token/menu`, `POST /public/tables/:token/orders`) tem limite próprio, no máximo 10 pedidos abertos por mesa e não permite que pedidos anônimos alterem clientes existentes.
- CRM e LGPD: `GET|POST /customers`, `GET|PATCH /customers/:id`, pontos de fidelidade (1 por real inteiro ao concluir o pedido), `GET /customers/:id/export` e `POST /customers/:id/anonymize` (gerência). Ao ficar `READY`, pedidos com cliente enfileiram a mensagem `order_ready` no outbox.
- Compras e inventário: `GET|POST /purchasing/suppliers`, `GET|POST /purchasing/orders`, `POST /purchasing/orders/:id/receive|cancel`. O recebimento atualiza estoque, custo médio ponderado e gera conta a pagar. `POST /inventory/counts` aplica inventário guiado com ajustes auditáveis.
- Cupons e reservas: `GET|POST|PATCH /coupons` (percentual ou fixo, validade, mínimo, limite de usos aplicado atomicamente) e `GET|POST|PATCH /reservations` (bloqueia a mesma mesa em janela de 90 minutos e respeita capacidade).
- Permissões por perfil (`apps/api/src/lib/permissions.ts`): gerência (`ADMIN`, `MANAGER`) cadastra; financeiro acessa financeiro/relatórios/compras; caixa e garçom vendem; cozinha acessa KDS e fila; entregador acessa entregas.
- WhatsApp: `apps/api/src/lib/whatsapp-cloud.ts` implementa a API oficial (Cloud API) com templates aprovados. Configure `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID` e `WHATSAPP_TEMPLATES` (JSON, ex.: `{"order_ready":{"name":"pedido_pronto","language":"pt_BR","params":["customerName","orderCode"]}}`) e execute `npm run worker --workspace apps/api` (um único processo). Sem configuração a fila permanece `QUEUED`; falhas ficam `FAILED` e podem ser reenviadas em `POST /whatsapp/outbox/:id/retry`. O adaptador foi testado com resposta simulada da API; valide com seu número/templates reais antes de produção.
- Usuários e escalas: `GET|POST|PATCH /users` (apenas administradores concedem `ADMIN`/`MANAGER`; ninguém altera o próprio perfil). Um usuário pode vincular opcionalmente um funcionário ativo no mesmo tenant e escopo; o vínculo é único, auditado e pode ser removido. Funcionário não precisa de login; o vínculo não altera automaticamente permissões nem desativa acesso. `GET|POST|PATCH|DELETE /shifts` (sem sobreposição por funcionário, máximo de 16h).
- Estoque avançado: cancelar pedido devolve ao estoque o consumo registrado e libera o uso do cupom, e exige estornar antes pagamentos confirmados (`POST /cash/payments/:id/refund`, só registro contábil). `POST /inventory/transfers` move estoque entre cadastros de ingredientes com custo médio. Opções de adicional podem consumir ingrediente (`ingredientId` + `ingredientQuantity`).
- Rateio: `PATCH /units/:id` define `serviceFeePercent` e `waiterSharePercent`; `GET /reports/service-fee-distribution` separa a parte do atendente e o fundo restante, e calcula comissão com `commissionPercent` do usuário.
- Auditoria: `GET /audit` oferece histórico somente leitura, paginado e filtrável por ação, tipo de registro, responsável e período. Restrito a administradores e gerentes sem escopo de unidade; os resultados nunca incluem dados de outras empresas.
- Autenticação: login por e-mail ou nome de usuário (case-insensitive), usuários inativos/bloqueados e tenants indisponíveis recebem erro genérico de credenciais. Contas `MASTER_ADMIN` precisam configurar TOTP no primeiro login e apresentar o código a cada novo login; segredos TOTP são protegidos por AES-256-GCM, sessões Master antigas são rejeitadas e códigos de recuperação aleatórios são mostrados uma única vez, armazenados como hashes e consumidos atomicamente. Login, configuração e verificação têm limites de tentativa. O seed Master usa segredo configurado localmente, força troca no primeiro acesso e registra somente o evento da troca, nunca senhas. A sessão JWT expira em 8 horas; senha alterada invalida tokens de sessão e desafios MFA anteriores.
- Recuperação de senha: `POST /auth/forgot-password` envia um link SMTP de uso único, limitado a 30 minutos, e responde de forma genérica para não revelar se o e-mail existe. `POST /auth/reset-password` valida o token, aplica a mesma política de senha forte, registra auditoria e invalida todas as sessões da conta. Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_FROM` e, quando exigido, `SMTP_USER`/`SMTP_PASSWORD`; defina `RM_RESTAURANT_URL` e `RM_ADMIN_URL` para formar os links corretos. Sem provedor e URLs configurados, a API responde indisponível e não finge envio.
- Pagamentos online por adaptador: `apps/api/src/lib/providers.ts` define `PaymentProvider`; registre implementações reais em `apps/api/src/providers.config.ts`. Sem adaptador, `POST /payments/charges` responde 501. Webhooks em `POST /payments/webhook/:provider` recebem o corpo bruto e o adaptador deve validar a assinatura.
- Módulo fiscal (`/api/v1/fiscal`, módulo `fiscal`): NF-e (55) e NFC-e (65) por um `FiscalProvider` (`emit`, `consult`, `cancel`, `correct`, `inutilize`, `testConnection`). O adaptador **Focus NFe** (`lib/fiscal-focus.ts`) vem registrado (desligue com `FISCAL_FOCUSNFE_DISABLED=true`); cada empresa informa o próprio token, e o certificado A1 também deve estar cadastrado na conta Focus. Configurações em *Configurações da empresa → Fiscais* (`GET|PUT /fiscal/settings`): emitente, ambiente (homologação/produção; produção exige configuração completa), certificado A1 validado e guardado criptografado (`POST /fiscal/settings/certificate`, requer `FISCAL_ENCRYPTION_KEY`), CSC, padrões por modelo, regra tributária padrão e comportamento fiscal do PDV (`FISCAL`, `NON_FISCAL`, `ASK`; decisão gravada por venda em `POST /fiscal/orders/:id/checkout`). Numeração por modelo e ambiente (`/fiscal/numbering`, só avança). A emissão usa o id do documento como referência idempotente; retorno perdido deixa o documento `PROCESSING` (sem protocolo) e ele é sempre consultado antes de reenviar, mantendo o número. Com contingência ativa, falhas de comunicação da NFC-e ficam `CONTINGENCY` até `POST /fiscal/documents/transmit`. Também: consulta individual/em lote, cancelamento, CC-e (NF-e), inutilização validada (`/fiscal/inutilizations`, também pelo PDV), histórico em `FiscalEvent` com XML de cada evento e exportação ZIP dos XML originais (`GET /fiscal/xml/export`). As regras tributárias guardam ICMS/ST/FCP, PIS/COFINS, IPI, IBS/CBS/IS, cClassTrib, cBenef e vigência; o cálculo e a validação legal ficam com o provedor/SEFAZ.
- Marketplaces: crie chaves em `POST /integrations` e receba pedidos em `POST /inbound/:provider/orders` (Bearer `rmint_...`, idempotente por `externalId`, itens mapeados por `Product.code`, preços do nosso catálogo, taxa de entrega informada pelo parceiro, cria o job de entrega). Produtos com grupos de adicionais obrigatórios não podem ser mapeados. Devolução de status ao marketplace (ex.: aceitar/despachar no iFood) exige a API do parceiro e não está implementada.
- WhatsApp: `POST|GET /whatsapp/outbox`. O endpoint apenas enfileira um registro auditável; envio real requer adaptador de provedor oficial e worker configurado.
- Financeiro e relatórios: `/financial` permite cadastrar contas a pagar/receber e registrar baixa integral, inclusive de contas geradas por compras. `GET|POST /financial/entries` aceita filtros `type`, `status`, `page` e `pageSize`; `POST /financial/entries/:id/settle` registra a baixa de uma conta aberta com auditoria e escopo de empresa/unidade. A baixa é gerencial, não movimenta dinheiro nem concilia banco. Resumo em `GET /financial/summary`; relatórios em `GET /reports/overview?from=ISO&to=ISO` e `GET /reports/waiters?from=ISO&to=ISO`. O rateio atual limita-se à divisão atendente/fundo descrita acima.

- Licenças e módulos (somente Master): `GET /tenants/modules/catalog`, `GET|PUT /tenants/:id/license` e a tela `/licenses`. Cada empresa pode ter uma licença (`PENDING`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `CANCELLED`), validade, limites de unidades/usuários e módulos contratados. A API aplica a restrição em `requireAuth` (por prefixo de rota) e no login, e os limites na criação de unidades e usuários; ocultar menus não é o controle. Empresas sem licença continuam com acesso integral (ambientes anteriores ao licenciamento) e nenhum dado é apagado por suspensão ou vencimento. Cada alteração gera `LICENSE_UPDATED` na auditoria. Ainda não implementados: chaves offline assinadas, solicitação com código, planos/preços, sincronização com confirmação e financeiro do SaaS. Rotas públicas (QR de mesa) e de máquina (agente de impressão, webhooks) não passam por essa verificação de módulos.

Rotas privadas exigem token Bearer. Os escopos tenant/unidade vêm do usuário autenticado no banco. O login limita tentativas a 10 por 15 minutos; a API aplica um limite geral de 300 requisições por 15 minutos, ambos em memória por processo. CORS aceita origens configuradas, o corpo JSON tem limite e erros internos não são expostos ao cliente. Para múltiplas instâncias, configure um armazenamento compartilhado de limites; atrás de proxy, ajuste e teste `trust proxy` de acordo com sua topologia e aplique limites no gateway antes de expor a API. Há testes de integração com PostgreSQL real cobrindo isolamento entre empresas, permissões, pedidos, impressão, QR, compras e reservas; amplie-os para os demais módulos antes de produção.

- RM Smart Migration (`/api/v1/migrations`, somente MASTER_ADMIN; tela em RM Painel Admin › Cadastros › Migração de dados, ou em Empresas › “Migração de Dados”): motor único de migração para qualquer restaurante, com oito grupos de dados — **Produtos e estoque** (produtos, categorias e subcategorias, custo, margem conferida, estoque mínimo, fornecedor vinculado, saldo inicial como movimento `ADJUSTMENT` de abertura), **Clientes** (CEP/cidade/UF/WhatsApp; nunca atribui consentimento de marketing), **Fornecedores** (fantasia, IE, endereço, contato, dados comerciais), **Contas a pagar**, **Contas a receber** e **Estrutura financeira** (categorias e subcategorias financeiras, centros de custo, contas bancárias com saldo inicial). Fluxo em cinco etapas: sessão por restaurante → envio de arquivos (`POST …/files?name=`, corpo binário) → `analyze` → revisão/aprovação do mapeamento (`PUT …/mapping`) → `preview` (nada é gravado; mostra totais financeiros, saldos iniciais e relacionamentos) → revisão de registros (`PATCH …/records/:id`) → `approve` com `confirm: "EXECUTAR"` e `backup` → `execute`/`resume` → relatório (`report`, `report.csv`, `report.pdf`) → `rollback` com `confirm: "REVERTER"` e `purge-files`. Todas as rotas ficam em `/tenants/:tenantId/sessions/:id/…`; a sessão é sempre buscada junto com o tenant. Código em `apps/api/src/lib/migration/`: `readers.ts` (CSV/TXT, XLSX, JSON, XML e dumps SQL MySQL/PostgreSQL lidos de forma estática — nada é executado; XML com DTD é recusado), `mapper.ts` (nome **e** conteúdo, relações entre tabelas, colunas sensíveis nunca mapeadas, modelos aprovados reutilizados só para a mesma estrutura), `ai-assist.ts` (reaproveita `currentAiProvider()` só para colunas ambíguas; amostras mascaradas; validado contra o modelo real; limitado a 70% e sempre para revisão; nunca inventa valores, datas, documentos ou relações), `fields.ts` + `pipeline.ts` (normalização determinística com regra/justificativa, regras financeiras, duplicados e conflitos), `executor.ts` (lotes, uma transação por registro, retomada sem duplicar, cancelamento efetivo, um `RUNNING` por restaurante por índice parcial, validação pós-migração e reversão seletiva) e `report.ts`.
- Regras financeiras da migração: o lançamento usa o próprio `FinancialEntry` (tipo `EXPENSE` = a pagar, `INCOME` = a receber) com as colunas aditivas fornecedor, documento, parcela/total, emissão, juros, desconto, centro de custo, conta bancária, forma e observações. Datas e valores históricos são preservados (nunca “hoje”); nenhum pagamento é inventado: pago sem data é rejeitado, pago sem valor/contradições (pago a menos/a mais, aberto porém quitado, pagamento futuro, cancelado com baixa) ficam como divergência para decisão humana; pagamento parcial permanece `OPEN` com o valor pago real e a data do último pagamento vai para as observações; “vencido” é calculado pelo RM. Parcelas ausentes de um documento são apenas sinalizadas. Datas `dd/mm` vs `mm/dd` só são lidas como `mm/dd` quando a própria coluna prova; senão vale `dd/mm/aaaa` com alerta.
- Backup: em produção (`NODE_ENV=production`, ou `MIGRATION_REQUIRE_BACKUP=true`; `false` desliga) a aprovação só é liberada por um backup **gerado e validado pela própria plataforma** para aquele restaurante e aquela migração (`POST …/sessions/:id/backups`). O backup exporta, em um snapshot consistente, todas as tabelas que o motor grava (categorias, produtos, movimentações de estoque, clientes, fornecedores e estrutura/lançamentos financeiros) apenas do `tenantId` da sessão, grava um arquivo `.rmbk` (NDJSON + gzip, AES-256-GCM com `MIGRATION_BACKUP_ENCRYPTION_KEY`, em `MIGRATION_BACKUP_DIR`, fora do banco), confere o SHA-256 e a estrutura do arquivo, **restaura uma cópia em ambiente isolado** (banco separado `MIGRATION_BACKUP_VERIFY_DATABASE_URL`, ou, se ausente, um esquema temporário descartado ao final) e compara contagens e hashes por tabela, relacionamentos e isolamento do tenant. A evidência fica em `MigrationBackup` (status `VERIFIED`/`FAILED`/`INVALID`). A autorização é bloqueada sem backup, com backup falho, corrompido, truncado, ausente, de outra empresa/sessão/banco, mais antigo que `MIGRATION_BACKUP_MAX_AGE_MINUTES` (padrão 60) ou sem restauração concluída; a integridade do arquivo é reconferida também ao iniciar a execução. A declaração manual do operador deixou de ser aceita. Referências de snapshot do Neon continuam recomendadas como proteção adicional, mas não liberam a migração. Limite: o backup cobre apenas as tabelas que a migração altera (não substitui o backup completo do banco).
- Auditoria da migração (somente MASTER_ADMIN, sempre por restaurante e sessão): `GET …/sessions` (paginado, filtro `status`), `GET …/sessions/:id/events` (linha do tempo paginada, `order`, `type`, com o nome de quem executou cada ação; falhas, interrupções, bloqueios de aprovação/execução e eventos de backup ficam registrados), `GET …/report` (contagens por módulo, erros e motivos, quem criou/aprovou/executou, e a situação dos backups da sessão), `report.csv` e `report.pdf`. Os eventos e o `AuditLog` ficam no banco, sempre com o `tenantId` da sessão; o histórico não é alterado por nenhuma rota.
- Reversão: remove apenas o que a migração criou, na ordem lançamentos → produtos → clientes → fornecedores → contas bancárias → centros de custo → categorias, e bloqueia (listando o motivo) o que foi usado ou alterado depois: lançamento baixado/editado depois (comparação de valores e `updatedAt`), fornecedor/cliente/conta/centro/categoria ainda vinculados, produto vendido ou movimentado, etc.

- Formação de preço e rentabilidade (`/api/v1/pricing`, perfis financeiros, módulo `profit`; tela em Inteligência › “Formação de preço e rentabilidade” e aba “Custos e margens” no cadastro do produto): a margem é **sobre o custo**; tributos, taxa de cartão, comissão, custo operacional % e outras despesas variáveis incidem sobre o preço de venda e são calculados “por dentro” — `preço = (custo total + custo fixo por unidade + custo × margem) ÷ (1 − soma dos %)`; o preço mínimo é o ponto de equilíbrio e a soma dos % igual ou acima de 100% é recusada. ML = (preço − custo) ÷ custo; MLA = resultado líquido ÷ custo. O arredondamento do recomendado é sempre para cima. Os padrões da empresa reaproveitam `products.defaultMarginPercent` e a seção `profit` (tributos e cartão) e acrescentam a seção `pricing`; cada produto pode sobrescrever (campo em branco herda). Simulações (`POST /pricing/simulate`, `POST /pricing/bulk/preview`) nunca gravam; alterar o preço oficial (`POST /pricing/products/:id/apply-price`, `POST /pricing/bulk/apply`) exige `confirm: true`, grava `PriceHistory` e auditoria, e a aplicação em massa recalcula no servidor, confere a contagem simulada e é atômica. Cada item de venda congela o custo (`OrderItem.unitCost` = custo + frete + outras despesas de aquisição) para que o lucro de vendas antigas não seja recalculado com o custo de hoje. Testes: `apps/api/src/lib/pricing.test.ts` (sem banco) e `apps/api/src/routes/pricing.integration.test.ts` (`RUN_DB_TESTS=1`).
- Configuração de produção (fail-fast): com `NODE_ENV=production` a API (`apps/api/src/lib/env-check.ts`, chamada na inicialização) recusa iniciar e lista **apenas os nomes** das variáveis inválidas — `JWT_SECRET` (≥ 32 caracteres, sem valor de exemplo/baixa entropia), `MFA_ENCRYPTION_KEY` e `FISCAL_ENCRYPTION_KEY` (32 bytes), `DATABASE_URL` (Neon exige `sslmode=require`), `CORS_ORIGIN` (origens exatas, sem `*`), `RM_RESTAURANT_URL`, `RM_ADMIN_URL`. Ausência de `MIGRATION_BACKUP_DIR`/`MIGRATION_BACKUP_ENCRYPTION_KEY` gera aviso e a RM Smart Migration permanece bloqueada. Em runtime use o pooler do Neon; Prisma Migrate deve usar a conexão direta (a configuração `directUrl` no schema ainda depende de autorização). Vercel: `API_INTERNAL_URL` em Web e Admin (Preview → API de staging). A lista completa de nomes está em `.env.example`.
- RM Inteligência e permissões: todas as rotas de `/intelligence` exigem o mesmo perfil do módulo Financeiro (ADMIN, MANAGER, FINANCE), verificado na API antes de qualquer consulta ou envio a modelo; o perfil é relido do banco a cada requisição (rebaixamento vale na hora). Perguntas diretas ou indiretas de outros perfis recebem 403 com a mensagem de falta de permissão e geram `AuditLog` `INTELLIGENCE_ACCESS_DENIED` (rota e perfil, nunca o texto da pergunta). Não há cache de dados compartilhado entre usuários. Testes: `intelligence.integration.test.ts`.
- RM Cliente VIP e fidelidade (`/crm`, rotas `/customers/:id/loyalty`, `/customers/campaigns`): cada compra concluída credita pontos conforme `settings.loyalty` (pontos por R$ 1,00) e grava uma linha no extrato `LoyaltyEntry` (compra, resgate, expiração, ajuste, estorno), sem crédito em duplicidade por pedido. O resgate (mínimo configurável) debita o saldo e gera um cupom de valor fixo e uso único no motor de cupons existente; a validade zera o saldo de quem ficou X dias sem comprar e fica registrada; ajustes manuais exigem gerente e justificativa e nunca deixam o saldo negativo. O cadastro tem data de aniversário e as campanhas (aniversariantes do mês, clientes inativos) listam só quem deu consentimento de marketing. `PATCH /customers/:id` não altera mais o consentimento quando o campo não é enviado.

- Migração: funcionários e histórico de vendas (grupos 7 e 8): **Funcionários** entram só como cadastro (nome, CPF, telefone, e-mail, cargo, admissão, situação) — nenhum usuário, senha ou permissão é criado; **Histórico de vendas** importa `SALE` (número, data original, total, desconto, taxas, cliente, forma de pagamento, situação) e `SALE_ITEM` (venda, produto por código/nome, quantidade, preço) como pedido `MIG-<número>` já finalizado ou cancelado, com a data original, sem baixa de estoque, sem ticket de produção, sem impressão e sem documento fiscal. O pagamento é gravado como no original (`integrated=false`, sem NSU/autorização) e, se a origem não informar a forma de pagamento, nenhum pagamento é inventado e o registro fica sinalizado para revisão. O custo do item de uma venda antiga fica vazio (não é estimado). Itens exigem venda e produto já existentes; a reversão remove itens → vendas → funcionários e bloqueia venda que recebeu pagamento depois. Teste: `apps/api/src/routes/migrations-sales.integration.test.ts`.
- RM Smart TEF (`/api/v1/tef`, módulo `integrations`; tela em Integrações › TEF, e pagamento com cartão no PDV): arquitetura de adaptadores (`apps/api/src/lib/tef/adapter.ts`), configuração por empresa com campos dinâmicos por provedor, credenciais criptografadas (nunca devolvidas nem registradas), status da integração (não configurada → aguardando credenciais → configurada → em testes → homologada → produção habilitada / com falha; “homologada” exige teste de comunicação bem-sucedido e evidência escrita, só pelo administrador, e nunca vale para o simulador). Fluxo: `POST /tef/transactions` (chave de idempotência obrigatória; reserva o saldo do pedido; pagamento misto com dinheiro/PIX/cartão sem exceder o total) → o provedor responde → **só uma aprovação validada** (identificador, valor, NSU e autorização para cartão, NSU único por empresa) cria o `Payment`, atualiza o fiado/financeiro e o caixa aberto; negada, sem resposta ou desconhecida nunca vira pagamento. Timeout/comunicação interrompida nunca reenvia a cobrança: a transação fica `TIMEOUT/UNKNOWN`, `POST /tef/transactions/:id/sync` consulta o provedor e a recuperação é idempotente. Estorno (`POST /tef/transactions/:id/cancel`, perfis financeiros, motivo + confirmação) só altera financeiro/caixa depois da confirmação do provedor e mantém o vínculo com a transação original; o estorno manual de um pagamento TEF é bloqueado; documento fiscal autorizado é apenas sinalizado (não é cancelado automaticamente). `GET /tef/monitor` e `GET /tef/reconciliation` (aprovação não é liquidação bancária). Dados reais do pagamento (`Payment.integrated/nsu/authorizationCode/cardBrand/acquirerCnpj/installments/pixEndToEnd/terminalId`) alimentam o `detPag` da NFC-e/NF-e (`tpIntegra=1`, CNPJ da adquirente, `tBand`, `cAut`) e o Focus NFe; dado ausente interrompe a emissão em vez de ser presumido. **Nenhum provedor real vem implementado** (SiTef, PayGo, Stone, Cielo, Rede, Getnet… exigem SDK/API, credenciais, contrato, PinPad e homologação próprios): o simulador `mock` só existe com `TEF_ENABLE_SIMULATOR=true` fora de produção, suas transações são marcadas `simulated` e nunca alimentam o fiscal. Para integrar um provedor, implemente `TefAdapter` e registre-o em `providers.config.ts`. Variáveis: `FISCAL_ENCRYPTION_KEY` (credenciais), `TEF_TIMEOUT_MS` (padrão 90000), `TEF_ENABLE_SIMULATOR`. Testes: `tef.integration.test.ts` e `nfe-payment.test.ts`.

- SUPER IA RM Intelligence (`/api/v1/ai`; tela em RM INTELLIGENCE › Central e 10 especialistas `/ai/<domínio>`): um orquestrador compartilhado (`apps/api/src/lib/ai/`) com **agente central** e **10 especialistas** lógicos (Gestão Financeira, Estoque, Controle de Lucro e Rentabilidade, Vendas, Compras e Reposição, Clientes, Delivery, Produção, Desperdícios e Gerencial), cada um com identidade, instruções, papéis, ferramentas e painel próprios. Os números vêm de consultas tipadas e determinísticas no backend (nunca do LLM); o modelo externo só **explica** dados agregados e sem dados pessoais. Cada resultado traz período, unidade, fonte, tipo (fato/estimativa) e limitações. Permissões por domínio, conferidas no backend a cada chamada e antes de qualquer ferramenta ou modelo: finanças/lucro/vendas/compras/gerencial = ADMIN/MANAGER/FINANCE; estoque e desperdício = gestão + financeiro + KITCHEN (valores monetários ocultos fora do financeiro); produção = `PRODUCTION_ROLES`; delivery = `DELIVERY_ROLES`; clientes = gestão + CASHIER (nomes só para gestão). Licença (módulo contratado) e permissão do usuário são checagens separadas (`intelligence`; `profit` para o especialista de lucro; sem linha de licença = sem restrição). Unidade: o usuário preso a uma unidade só vê a dela; só gestão/financeiro sem unidade fixa escolhe unidade, e apenas da própria empresa. **Economia e governança de IA**: roteamento por palavras-chave (modelo só classifica se nada casar e a IA externa estiver permitida), apenas os especialistas necessários (limite configurável), cache com chave tenant+unidade+perfil+período+**versão dos dados** (invalida sozinho quando os dados mudam), deduplicação de requisições simultâneas, narrativa reaproveitada para a mesma pergunta/dados, modelo econômico (`AI_MODEL_SIMPLE`) para perguntas de um especialista e modelo capaz (`AI_MODEL`) para consolidações, limites diários persistentes no banco (estabelecimento/usuário/módulo), sem retry automático de chamadas possivelmente cobradas, circuit breaker, timeout e fallback para a análise determinística, consentimento opt-in da empresa (`ai.externalConsent`) e chave para desligar a IA externa. Consumo medido (`AiUsageEvent`: chamadas, tokens informados pelo provedor ou estimados e marcados, cache hit/miss, latência, erros) no painel “Consumo e controles”; histórico privado por empresa e usuário com retenção configurável. Variáveis: `AI_API_KEY`, `AI_MODEL`, `AI_BASE_URL` (já existentes), `AI_MODEL_SIMPLE` (opcional). Testes: `lib/ai/ai-engine.test.ts`, `routes/ai.integration.test.ts`, `apps/web/lib/menu-catalog.test.mjs`.

- Permissões financeiras (revisão transversal): `apps/api/src/lib/redact.ts` remove campos de custo (`cost`, `unitCost`, `averageCost`, `freightCost`…) das respostas de produtos, estoque, pedidos, produção, mesas, delivery, catálogo e painel para perfis sem permissão financeira; a SUPER IA, o monitor TEF e as listas de transações respeitam o mesmo critério (caixa vê só as próprias transações TEF). Exceção operacional documentada: o caixa enxerga valores de pagamentos (`/cash/payments`). `financial-permissions.integration.test.ts` percorre todas as rotas GET sem parâmetro de cada perfil contra valores-sentinela e tenta perguntas indiretas/manipuladas às 10 especialidades.
- Fechamento oficial do caixa: `POST /cash/sessions/:id/close` só é aceito de uma sessão iniciada em **computador** (o login classifica o cliente pelo User-Agent — `apps/api/src/lib/client-kind.ts` — e grava `client` no token assinado). Celulares, maquininhas/POS e chamadas diretas à API (curl, scripts, token forjado sem `client`) recebem 403 `CASH_CLOSE_DESKTOP_ONLY` e a tentativa fica no log de auditoria (`CASH_CLOSE_DENIED`). Abertura de caixa e recebimentos continuam disponíveis nos demais clientes. Limite honesto: o User-Agent é informado pelo cliente; um script que finja ser um navegador de computador com credenciais válidas passa — a trava impede o fluxo acidental/por dispositivo, não substitui controle de acesso por rede/dispositivo.
- TEF — operação: `POST /tef/transactions/:id/undo` (desfazimento de cobrança ainda não resolvida: só fecha com confirmação do provedor e nunca desfaz uma aprovada — nesse caso orienta o estorno), `POST /tef/recover` (varredura que consulta o provedor para transações pendentes/sem resposta e registra aprovações perdidas uma única vez; sem reenvio de cobrança), `GET /tef/events` (log sem valores), voucher como forma TEF (depende do provedor), pagamento com cartão também na tela Caixa e eventos/recuperação/comprovante em Integrações › TEF. Aprovação recuperada depois do fechamento da venda emite o documento fiscal conforme a regra da empresa (`emitAfterPayment`; `ASK` continua decisão humana, `NON_FISCAL` nunca emite).
- Impressão de comprovantes (`POST /printing/receipts/{tef/:transactionId|order/:orderId|fiscal/:documentId}`): bobinas 55, 58 e 80 mm (30/32/48 colunas), vias e rodapé em Configurações › Impressão, impressora tipo “Recibo” por unidade (ou escolhida), original impresso uma única vez (chave de deduplicação com índice único parcial) e reimpressão com motivo obrigatório, marcada “REIMPRESSÃO” e auditada. Comprovante TEF é o do RM (dados validados da transação), não o do adquirente; documento fiscal só imprime se autorizado e em homologação sai marcado “SEM VALOR FISCAL”. Impressão automática do comprovante TEF por terminal (`printing.autoPrint`). Homologação com impressoras físicas e agente instalado não foi feita aqui.
- Fiscal: o documento nunca é completado com pagamento “Outros” (99) inventado: pedido não totalmente pago, ou cujo total inclui taxa de serviço/couvert/entrega que o documento não carrega, é recusado com `FISCAL_PAYMENT_MISMATCH` antes de consumir numeração (NF-e sem pagamento usa `tPag` 90). Validação XSD/SEFAZ real continua dependendo de certificado e do ambiente de homologação.
- Gateway único de IA (`apps/api/src/lib/ai/gateway.ts`): especialistas, RM Assistente (`/intelligence/business`), robô do WhatsApp e mapeamento de colunas da migração passam pelo mesmo portão — consentimento da empresa, chave liga/desliga, limites diários persistentes (empresa, **unidade**, usuário, módulo; `AI_DAILY_LIMIT` só pode reduzir), disjuntor, tamanho máximo do prompt (recusa em vez de truncar), reaproveitamento e medição. `POST /ai/estimate` mostra a estimativa (caracteres÷4) antes da chamada; `GET /ai/usage/compare` compara períodos; tokens **reais** (informados pelo provedor) e **estimados** nunca são somados. Previsão de vendas e meta mensal (especialista de Vendas) trazem método, faixa de ±1 desvio-padrão e aviso de incerteza, ou “dados insuficientes”. `GET /ai/domains/:key/export.csv` exporta o painel respeitando as mesmas permissões (auditado).
- Migração por unidade: a sessão aceita `unitId` (validado contra as unidades do restaurante; `GET /migrations/tenants/:id/units`); vendas, pagamentos, lançamentos a pagar/receber, abertura de estoque e funcionários importados nascem na unidade escolhida e nada vai para as demais.
- Formação de preço × lucro: as duas telas se referenciam; `GET /pricing/settings` devolve `taxReview` (regime do cadastro fiscal só para revisão — nenhuma alíquota é presumida).

## Limitações relevantes

Maquininha própria/Smart POS: fora do escopo (somente TEF padrão). O fechamento oficial do caixa é exclusivo do computador, mas a identificação do cliente usa o User-Agent (veja acima).

Formação de preço: os tributos entram pelo percentual informado (o regime “Normal” do cadastro fiscal cobre Lucro Presumido/Real, sem cálculo automático de alíquotas). O rateio automático do custo operacional da empresa por produto não é feito: o custo operacional é informado em % ou valor fixo por unidade. Custo congelado só existe nas vendas feitas depois da migração `20261119230000_pricing_costs`; antes disso o lucro usa o custo atual ou a ficha técnica.

SUPER IA: sem provedor de LLM configurado só as análises determinísticas funcionam (nenhum token foi consumido nos testes automatizados: o provedor é simulado); o custo em moeda não é calculado (depende da tabela do provedor); o cache é por processo (várias instâncias não o compartilham, mas os limites e o consumo são persistentes); o tempo de preparo da produção é uma aproximação (o sistema não registra o início do preparo por item); `/intelligence` (RM Assistente) continua com seu próprio limite diário em memória e não passa pelo orquestrador; MASTER_ADMIN não acessa inteligência de restaurantes.

RM Smart TEF: nenhum provedor real está integrado nem homologado neste repositório; PIX integrado (EndToEndId) é guardado no pagamento, mas o leiaute 4.00 da NF-e não tem campo para ele; a conciliação com a liquidação do adquirente e o comprovante original do adquirente dependem do provedor (o RM imprime a sua via, com os dados validados); voucher/carteiras dependem de o provedor oferecê-los; a transmissão à SEFAZ em homologação não foi testada aqui (sem certificado/credenciais). Cancelar o pedido no RM não cancela sozinho a transação no adquirente nem o documento fiscal.

RM Smart Migration ainda **não** cobre: XLS antigo (BIFF), SQLite binário, `pg_dump -Fc`, arquivos protegidos por senha e conexão direta a banco externo (as mensagens do sistema explicam como exportar em formato compatível), nem mesas e comandas abertas, usuários/senhas, fichas técnicas, adicionais/combos, histórico antigo de movimentações de estoque, imagens/anexos, caixa/turnos históricos e documentos fiscais históricos (histórico de vendas e funcionários — só cadastro — são migrados), nem a área limitada de importação no painel do restaurante. Tabelas que misturam contas a pagar e a receber precisam ser exportadas separadamente. Lançamentos migrados não têm unidade (`unitId` nulo): aparecem para usuários de toda a empresa, não para usuários presos a uma unidade. O ponto de segurança é lógico (ids criados guardados por registro) — o backup do banco continua sendo responsabilidade da operação. Registros preparados (`MigrationRecord`, com os valores originais) ficam guardados para auditoria; `purge-files` descarta apenas o conteúdo dos arquivos enviados.


Estoque: consumo automático por ficha técnica e por adicionais ao iniciar o preparo, compras com custo médio, inventário guiado, transferências e estorno ao cancelar. Caixa e relatórios são gerenciais, não conciliação contábil. A emissão fiscal depende de conta ativa no provedor (Focus NFe) e homologação na SEFAZ; sem adaptadores reais não há cobrança PIX/cartão nem retorno de status a marketplaces; a regra de rateio de gorjeta é apenas a divisão atendente/fundo configurada por unidade. Não exponha em produção antes de executar a validação Prisma/TypeScript, migrações, testes de integração e revisão de segurança, incluindo permissões por perfil e escopo de unidades.

Antes de qualquer implantação, revise também `npm audit` e atualize dependências vulneráveis com testes de compatibilidade, configure HTTPS e segredos reais, verifique backups e restauração, e teste concorrência de caixa/pagamentos e isolamento entre tenants com um PostgreSQL real. Esta etapa é um endurecimento inicial, não uma certificação de prontidão para produção.

## RM Assistente — modo professor

O RM Assistente também ensina a usar o sistema (botão `?` no topo de qualquer tela, widget do dashboard e a aba RM Assistente). A base de conhecimento é gerada das telas reais: `scripts/generate-guide-screens.mjs` lê o menu (`apps/web/lib/menu-catalog.ts`) e cada página (`apps/web/app/*/page.tsx`: título, abas, campos e botões) e grava `apps/api/src/lib/guide/screens.generated.json`; os passo a passo ficam em `apps/api/src/lib/guide/procedures.ts`. O teste `guide.test.ts` falha se uma tela mudou e o índice não foi regenerado (`node --import tsx scripts/generate-guide-screens.mjs`) ou se um passo a passo cita menu, aba, campo ou botão que não existe. O guia só ensina: não altera nenhum dado.
